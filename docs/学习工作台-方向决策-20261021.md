# 学习工作台 · 方向决策（2026-10-21）

> 讨论：把学习系统做成「类 OS」——在工作台里打开应用/网页，Agent 基于此分析，并提供特定服务。
> 结论：**不做 OS/通用壳；做「学习上下文工作台 / 学习 Agent 平台」。**

## 一、拍板结论

学习工作台继续是一个**垂直的学习工作台**，不是通用操作系统。重点投入三层：

| 层 | 内容 | 优先级 |
|---|---|---|
| **Context（上下文）** | 当前表面、材料/题型/句子、选区、最近动作、学习状态；插件可贡献，Agent 可读 | 高 |
| **Service（服务）** | 翻译、查词、解释、分析、出题、复盘、资料检索；统一接口，用户与 Agent 共用 | 高 |
| **Surface（表面）** | 现有插件页 + 少量值得嵌入的网页（只对特定站点做上下文抽取） | 中 |

「窗口管理 / 应用商店 / 任意 app 托管」不做——浏览器和 OS 已经在做，且不是学习场景的瓶颈。

## 二、为什么不做 OS

1. **能力和场景不匹配**：进程隔离、权限、沙箱、驱动、多用户这些是平台级工程；现在的插件体系已经提供了「应用」的价值，缺的是应用之间的共享上下文。
2. **通用 Agent OS 是巨头战场**：Windows Copilot、Apple Intelligence、Edge/Chrome AI、Arc/Comet 都在做；个人/学生项目做通用壳没有胜算。
3. **全域可见的代价**：网页提示词注入、隐私、token 成本、上下文噪音、误操作；OS 化会把这些风险放大。学习工作台应保持「显式挂载上下文」。
4. **机会成本**：做壳的时间会挤掉六级、网工、资料库这些真正产生学习价值的功能。

## 三、最小验证：六级精听（1–2 周）

不先写平台，先用一个具体场景验证「上下文 + 服务」是否真的改变日常使用：

1. **自由提问**：精听页加输入框，自动带当前试卷/题型/当前句/循环统计，回答复用现有分析面板——同时解决「断点鸡肋」和「分析结果丢失」。
2. **划词翻译**：选中单词 → 即时翻译，可一键预填生词本释义。
3. 连续用 1–2 周：
   - 如果每天都用 ⇒ 再把「上下文快照 + 服务接口」抽象成平台；
   - 如果还是直接问 AI 更快 ⇒ 停止平台化，继续打磨单点功能。

## 四、非目标（明确不做）

- 不做任意应用/网页的通用宿主、窗口管理器、应用商店。
- 不做默认的全域屏幕/键盘/网页采集；上下文必须显式挂载或按需授权。
- 不为了「平台」重写现有插件工作台；优先复用 FastAPI、插件注册表、统一库、Agent 工具循环。
- 不追求多用户、沙箱、插件市场等平台能力。

## 七、Agent 接入策略（2026-10-21 追加）

讨论「用自研 Agent 还是直接接入 Claude / Codex」后的结论：

- **框架用自己的，模型不站队。** 产品运行时 = 自研 `learnsys/agent`；模型可插拔：DeepSeek 默认（便宜、国内可达），Claude 作为可选「深度分析」；用真实任务做 A/B 后再定默认值。
- **Claude Code / Codex 是客户端，不是运行时依赖。** 开发期用 Claude Code 改代码/跑测试；产品不要求用户装它们，自研 Agent 必须能独立运行。
- **MCP 优先。** 工作台把上下文与服务暴露成 MCP server（资料检索、六级上下文、翻译/查词、复盘、错题），Claude Code / Codex 通过 MCP 接进来；工作台不需要猜它们的内部状态，也不接管它们的登录/沙箱/版本。
- **可选增强：深度分析。** 用户显式点「让 Claude/Codex 深度分析」时才走 headless CLI 或 API；默认只读、限定目录、超时、记录成本与审计，不静默跑 shell/改文件。
- **协调先做路由，后做编排。** P1：MCP server + 自研 Agent 默认；P2：可选深度分析；P3：按任务/成本/可用性路由 + A/B 评测；P4：只有评测证明有效才做 draft + reviewer 的双 Agent，不做全自动任务分解。
- **不做**：把多个 Agent 的全自动协调当前置核心；让学习 App 默认获得改文件/执行命令的权限；为了「Agent 平台」重写现有工作台。
- 与方向的关系：Agent 接入属于 **Service 层**，服务于 Context + Service + Plugin 的主线；枢纽是上下文与服务，不是「所有 Agent 的老板」。

## 八、Agent 中枢修订（2026-10-27）

负责人提出「把工作台变成电脑上 agent 的中枢，能调动本机 agent」。对第七节做如下修订，
不推翻其余结论：

- **中枢 = 只读派活台**：用户显式创建任务，工作台启动 Claude Code / Codex，展示流式过程，
  保存结果；**不是全自动编排器**。
- 外部 agent 仍是**可选能力**：没装 / 没开时工作台照常工作；不接管登录、密钥、沙箱、版本。
- 默认**只读**：Claude `--restricted --permission-mode plan`，Codex `--sandbox read-only`；
  写文件 / 跑命令留 P26.2，且要逐条审批。**2026-10-28 落地口径**：Claude 用 PreToolUse 钩子
  逐条审批；Codex `exec` 无人工审批通道，本版用 `workspace-write` 只允许在所选目录内写、
  整任务授权，逐条审批等以后接 app-server。不把 Codex 的整任务授权写成「逐条确认」。
- **先派活、再路由、最后编排**：P26.1 只读派活 → P26.2 可写 + 审批 → P26.3 路由 / 队列 →
  P26.4 才讨论自动编排；没有前三个阶段的数据不做全自动编排。
- 第七节「枢纽不是所有 Agent 的老板」仍然成立：中枢是**用户意图的调度台**，不是自动决策的老板。

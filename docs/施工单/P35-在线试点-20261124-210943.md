### fact-net-tcp-handshake · 通过
- **问**：用一句话解释 TCP 三次握手
  **答**：TCP 三次握手，就是双方各发一次、各确认一次，共三步，确认「你发得出、我收得到、我发得出、你收得到」四条通道都通，并同步初始序列号，之后才开始传数据。 三步具体是： 1. 客户端 → 服务器：SYN，seq=x（我想连，我的起始序号是 x） 2. 服务器 → 客户端：SYN+ACK，seq=y，ack=x+1（我收到了，我的起始序号是 y，等你从 x+1 开始） 3. 客户端 → 服务器：ACK，ack=y+1（收到你的了） 易错点：为什么不能两次？因为服务器发出 SYN+ACK 后并不知道客户端是否收到（客户端这时往往还没有实际数据要发，只有第三次 ACK 才能让服务器确认自己的发送方向也通），而且两次握手还可能被网络里滞留的旧 SYN 请求骗出半开连接。 （这道是概念题，和你的六级目标、错题本没有直接关联。）

- **问**：发送端重发的块应该会出现块大小不等的情况吧
  **答**：会出现，因为字面量段是**不按块长切的**，长度任意。 区分两种段： - **匹配段**：长度固定为 L，发送一个块号。 - **字面量段**：长度不固定，从「一个窗口大小 L 未匹配」到「很长一段连续都未匹配」都可能。发送端遇到未匹配时，窗口只前进 1 字节，继续试探下一个位置；一旦连续失败，它不会每次都单独发 1 字节，而是把这段连续未匹配的内容**累积成一个字面量**，一次发出去。所以字面量段的长度是任意的，从 1 到整个文件都有可能。 因此，拆出来的指令流是「块号 / 字面量」交替的混合序列，各段长度不等，只有块号段固定为 L。接收端不需要对齐块边界——它只是按指令顺序，把块号从旧文件读取并拷贝出来、把字面量原样写入，最终拼出的新文件长度由这些段的长度总和决定，跟旧文件的块划分毫无关系。 **顺带说清一个边界**：理论上，发送端每遇到一个未匹配的位置就发出这个长度为 1 的窗口内容

### fact-algo-block-plus1-text · 通过
- **问**：分块查找里，索引表用折半查找定位块时，平均查找长度写成 log2(n/s + 1) + (s+1)/2。为什么 log 里面还要加 1？
  **答**：**结论：log₂(n/s + 1) 里的「+1」并不是在块数上额外加一块——它的作用是表示每次比较都要访问索引（不论定位到哪一块），因此索引部分的成功平均比较次数要按「有序表折半查找」的标准结论计算。** 至于这个结论为什么带 +1，取决于你用的折半查找是哪种版本。你需要先确认：你课本里的折半查找平均查找长度（ASL）公式到底是 log₂(n+1)−1 还是别的。 **关键在于概念区分** - 分块查找（索引顺序表查找）的成功 ASL = **索引表查找 ASL + 块内顺序查找 ASL**，两部分相加而不是相乘。 - 块内部分：假设每块 s 个元素、等概率，顺序查找平均是 (s+1)/2，这部分没有争议。 - 索引部分：把 n/s 个块的块首关键字看成一张**有序表**，对它做折半查找。折半查找的成功 ASL 本身就带 log₂(元素总数+1) 这种形式，而那里的 +1 来自判定树：n

# 上下文预算（P0）

> 建立于 2026-11-04。目标：把「prompt 里塞了多少东西」变成可计算、可审计、可配置的一件事，
> 而不是六个文件里各写一个字符上限。

## 一、改之前的问题

| 问题 | 位置 | 后果 |
|---|---|---|
| 六处字符上限各写各的 | `prompts.py` 的 8000 / 6000 / 2000 / 1200，`loop.py` 的 8 轮 / 4000 | 中文和英文按同一个字符数截，中文容易超、英文浪费 |
| 工具结果原样回灌 | `turn.py::_handle_tool_call` | 8 步工具调用可能把上下文撑到几万 token |
| 工具 schema 没算进上下文 | 34 个 schema 每轮全量发送 | 实测约 **6000 token**，占 24K 预算的四分之一 |
| 历史只看轮数不看大小 | `loop.py::_history_messages` | 8 轮长回答可能比 8 轮短回答大十倍 |

## 二、现在的口径

**唯一落点**：`learnsys/prompt_budget.py`（不依赖 agent 包，`llm.config` 也能安全引用）。

| 函数 | 作用 |
|---|---|
| `estimate_tokens` | 中文≈1 token/字，其他≈1/3.5 token；刻意略高估 |
| `clip_tokens` | 按 token 裁剪，支持保留头 / 尾 / 头和尾，中间打「已截断」 |
| `fit_sections` | 多段共享预算：问题永不裁，其余按权重分配，小段没用完的额度还回去 |
| `tool_result_budget` | 单次工具结果上限 + 整轮工具结果上限 |
| `estimate_messages` | 估算 Anthropic messages 的 token（含 tool_result） |

**接入点**（全部走同一套常量，不再出现第二份上限）：

1. `agent/prompts.py`：系统提示词里的摘要 / 画像 / 长期记忆；用户消息里的截图 / 附件 / 上下文。
2. `agent/loop.py`：
   - 先装历史（独立预算），再扣系统提示词和**工具 schema**，剩余额度给「问题 / 上下文 / 截图 / 附件」；
   - `question` 永远不裁；预算实在不够时，审计里会看到 `requested > budget`，不会悄悄丢掉问题。
3. `agent/turn.py`：每次工具结果裁到 `tool_result_tokens`，整轮累计不超过 `tool_turn_tokens`；
   证据自检仍用**未截断的原文**，只有回给模型的文本会被裁。
4. `agent/finish_turn.py`：`done` 事件带 `prompt` 审计与 `tool_tokens`；
   `routes_agent/common.py` 把它写进 `agent_runs.trace_json` 的 memory 项，事后可查。

## 三、配置项（`设置.json` → `agent`）

| 键 | 默认 | 含义 |
|---|---|---|
| `prompt_budget_tokens` | 24000 | 本轮输入预算（不含模型输出） |
| `tool_result_tokens` | 3000 | 单次工具结果上限 |
| `tool_turn_tokens` | 12000 | 一轮所有工具结果合计 |
| `history_tokens` | 6000 | 历史窗口预算（仍保留「首轮 + 最近七轮」的选取规则） |

越界值会被夹到安全范围；不配置就是默认值。这些字段已出现在 `AgentConfig.public()`，
设置页以后可以直接加输入框，不需要再改后端。

## 四、实测（2026-11-04，生产库快照，不调模型）

构造压力场景：8 轮各 4000 字回答 + 30000 字附件 + 10000 字课堂上下文 + 5000 字摘要。

| 项 | 改前（按字符上限） | 改后（按 token 预算） |
|---|---|---|
| 系统提示词 | 5904 | 5904 |
| 工具 schema | 6008（未计入预算） | 6008（计入） |
| 历史 | 约 32000 | 5621（7 轮，长答裁到 800） |
| 当前用户消息 | 约 40000 | 12074 |
| **合计** | **约 84000** | **23637** |

审计输出（`turn.state.prompt`）：

```json
{"budget": 24000, "system_tokens": 5904, "tool_schema_tokens": 6008,
 "history_tokens": 5621, "history_turns": 7, "current_user_tokens": 6104,
 "user": {"sections": {
   "question":   {"before": 20,    "after": 20,    "clipped": false},
   "context":    {"before": 10000, "after": 3887,  "clipped": true},
   "attachment": {"before": 30000, "after": 2159,  "clipped": true}}}}
```

> 注意：这是**估算值**，不是服务端 tokenizer 的精确值；它比实际略高，用来留安全余量。

## 五、验证

- `tests/test_prompt_budget.py` 16 个测试：估算、裁剪、共享分配、历史窗口、工具结果、done 审计；
- 全量 **1676 测试通过**；
- `arch_report --check`、`layering_report.py` 通过；
- 既有测试 `test_agent_p1` 的「8 轮历史」契约保留，长历史才会触发丢弃。

## 六、已知限制与下一步

1. **估算不是精确 tokenizer**：中文按 1 token/字、英文按 1/3.5，偏差在 ±15% 左右；
   下一步可以接服务端返回的 `usage.input_tokens` 做校准，把「估算 vs 实际」写进流水。
2. **还没有 prompt caching**：DeepSeek 侧可能有自动缓存，但代码里没有显式 `cache_control`；
   系统提示词和 34 个工具 schema 每轮重复发送，是下一笔可省的成本。
3. **工具结果只裁不压缩**：现在是头尾保留 + 中间标记；下一步可以在裁之前做一次
   「提取结论/摘要」的轻量压缩，尤其是 `read_material` 和 `search_records`。
4. **没有跨轮工具结果**：历史仍只回放问/答对；追问「按刚才跑的结果」仍依赖答案正文。
   要不要把关键工具结果摘要写进历史，需要先看在线评测里这类追问的失败率。
